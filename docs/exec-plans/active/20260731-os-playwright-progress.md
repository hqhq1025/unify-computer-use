## 二、已实现的四个阶段

### P0 通道分家（`aa684e5`）

三条通道，**写进工具名、描述开头、以及每一条 Note**：

```
ACCESSIBILITY  按 element_index 定位   click / invoke_element_action / set_value
GUI            按窗口相对像素定位      click_xy / drag_xy / get_screenshot
KEYBOARD       不定位，落到当前焦点     press_key / scroll / type_text 回落
```

Note 带**两个正交标签**：`[a11y][semantic]` / `[gui][synthesis]` /
`[keyboard][synthesis]`。最要紧的一格是 **`[a11y][synthesis]`**——用树给的坐标
去合成点击。以前只有执行轴一个标签，这一格会被记成纯合成，
于是"agent 压根没用 a11y"与"用了但语义动作失效后回落"分不开。

接口变化：`click` 不再接受 x/y；新增 `click_xy`（**带命中回报**）；
`drag` → `drag_xy`。安全性上，原来那道整个禁掉裸坐标的环境变量闸门，
换成了**把 GUI 通道的坐标夹紧在窗口矩形内**——风险从"可能打到别的应用"
降为"最多打到本窗口边缘"，且不牺牲能力。

### P2 意图声明（`397d9a3`）

四个 a11y 通道工具各加一个可选 `element`（人类可读描述），服务端拿它
**交叉核对**下标解析到的东西。

判据**做错过一次**：第一版把 role 也算进匹配范围，被 "button" 这个词击穿
（声明里几乎必有、role 里也几乎必有），正要拦的情况照样放行——真机跑出来
才发现。现在只对**有名字**的元素比对 name+description，通用词表 30 个词
不计入区分性实词，无名元素整个跳过（它们的身份常来自旁边的 label）。
原则是**误拒比漏过更糟**，测试里正例比反例还多。

**真实 agent 在 100% 的 click 调用上自发填了这个参数**，
说明它可发现、可自然使用。

### P1 快照文法（`4b1f383`）

```
<index> <role> "<name>" [<states>] [desc="…"] [placeholder="…"]
              [actions=a,b] {x,y,width,height}: "<value>"
```

修的是一个真 bug：旧格式 `<idx> <role> <name> Description: <desc>` 里，
**名字本身可以含冒号**（实测 `panel PageShape: Weekday in school`），
名字与字段分隔符在词法上无法区分——我们发出去的是一种**歧义文法**。

顺带把几何从 45 字符压到 14 字符，**整棵树省 30%**（五个应用实测
27%–34%），信息不少一个字。

### 性能：裁剪判据先做廉价探测（`98b8d0e`）

矩阵测试第一次跑就抓到**一条真断链**：GIMP 的 `get_app_state` 38.4s，
**超过 Go 层 30s 的超时**——a11y 通道在 GAIL 上默认根本用不了。

定位：`record_for` 被调用 3162 次只产出 157 条记录，占渲染耗时 87%，
**95% 的开销当场丢弃**。而裁剪判据只用到四个字段（≈2.3ms），
却先付了完整的 8.45ms。改成先探测后取全量：**38.4s → 17.5s，行数一字不差**。

## 三、真实 agent 轨迹带来的两处修正（`bd42684`）

这是**只有真跑才能发现**的一类问题。

### ① `unknown element_index "128"` —— 27 个字符、零指引

agent 用了几步之前那份快照的下标，而树在动作后缩小了。对照之下，
下标**解析到别的控件**时的报错讲清了原因和出路。同样是"下标过期"，
两条路径的帮助程度不该差这么多。现在会给出当前快照的下标范围与该怎么办。

### ② "delivered-but-ignored" 说过头了，代价被量出来了

ctrl+s 之后这条 Note 断言"送达但被忽略、重复也没用"，而文件**其实存下来了**
（评估器判 1.0 就是证据）。agent 因此多花截图 + 点 Save 按钮**两步去自证**。

成因是该判据的结构性盲区：**格式类改动与文件状态根本不进 a11y 树**。
"树没变"推不出"没生效"，只能推出"树看不见"。改成把 agent 指向截图与外部真值。

**改完同一任务同一环境再跑：12 步 → 10 步，129.4s → 102.7s（-17% / -21%）。**
省掉的正是那两步自证。**过度断言的代价第一次被量出来。**

## 五、跑真实 agent 的坑（下次直接照做）

- **`--mcp-config` 根本不生效**。传文件或 JSON 字符串都试过，stream-json 的
  init 事件里 `mcp_servers` 始终是 `[]`，agent 一个 `mcp__` 工具都看不到，
  **却不报任何错**——它只会说"我没有这些工具"，看起来像模型的问题。
  可行做法：`claude mcp add <name> --scope local`（按目录存进 `~/.claude.json`，
  注册到一次性目录就不污染用户的正常项目）。
- **服务名不能叫 `computer-use`**，那是保留名，会被直接拒绝。
- **评估器要按文件加载 `slides.py`**，别走包的 `__init__`——它连带导入 chrome
  评估器，需要 `rapidfuzz` / `formulas`。
- **任务 JSON 的 `options` 必须原样传给评估器**。漏传 `examine_shape: false`
  会把一次成功记成 0.0，然后往错误的方向找原因。

## 六、与 Playwright 的对照（现状）

| 维度 | Playwright | 我们 | 判断 |
|---|---|---|---|
| 通道分层写进工具名 | `browser_mouse_*_xy` | `click_xy` / `drag_xy` | ✅ 对齐 |
| 快照文法 | `- role "name" [attr]` | `<idx> role "name" [attr]: "value"` | ✅ 对齐 |
| 意图声明 | `element` 参数 | `element` 参数 **+ 交叉核对** | ➕ 更强（它只用于可读性/权限） |
| 几何 | 默认不给，`boxes` 开关 | 默认不给，`boxes` 开关 | ✅ 对齐 |
| 稳定 selector | `target` 接 ref 或 selector | `element_index` 接下标或 `role "name"` | ✅ 对齐 |
| 通道可关 | `--caps=vision` | `OPEN_COMPUTER_USE_CHANNELS` | ✅ 对齐 |
| 动作后的效果判据 | 无（DOM 完备，不需要） | 五类失败分类 + 自动回落 + 双通道验证 | ➕ 更强（OS 上必须有） |
| 坐标命中回报 | 无 | `click_xy` 报出命中元素（标为提示） | ➕ 更强 |
| 通道权重 | 坐标是边缘 opt-in | **GUI 是一等公民** | ⚠️ **刻意不对齐**，见下 |

**唯一刻意不对齐的一条**：Playwright 敢把坐标做成边缘能力，是因为浏览器里
DOM 完备、一切可 ref 定位。OS 上这个前提不成立——已实测五例 a11y 结构性
看不见（GIMP 画布 canvas 节点为 0、VS Code 原生对话框与重启提示不在树里、
drag 的效果不进树、格式改动不进树）。**抄它的通道分层与命名纪律，
不抄它的通道权重。**

### 三项的实测收益

- **P3 几何 opt-in**：七个应用省 16–25%，合计 19%；叠加 P1 的 30%，
  从原格式累计省约 46%。真实 agent 在不带几何的树上重跑 OSWorld 得分仍是 1.0，
  观测 token 19565 → 14681（-25%）。
- **P4 selector**：语法与快照行逐字一致，抄下来就能用；歧义时列出候选而不是
  静默挑一个。
- **P5 通道开关**：关掉的通道其工具**从 tools/list 里消失**，不是调用时才拒——
  模型看得见的工具会去试，看不见就不会试。

## 七、这算不算 hybrid CUA——用轨迹回答

WeaveBench 的判据是**通道切换次数**（≥5）加**单通道硬封顶 0.4**。
两次成功任务的实测：

| 任务 | 步数 | a11y | gui | keyboard | **通道切换** |
|---|---|---|---|---|---|
| A 加右对齐标题 | 10 | 2 | 2 | 5 | 3 次 |
| B 标题移到底部 | 15 | 6 | 2 | 6 | **9 次** |

任务 B 的通道序列：
`a11y → a11y → keyboard → gui → keyboard → keyboard → a11y → a11y →
keyboard → gui → a11y → keyboard → keyboard → a11y`

### 最有说服力的是任务 B 第 8–13 步：三条通道协作完成同一个子目标

1. `set_value "15.12 cm"`（a11y 语义）写进 spin button
2. 点 OK（a11y 语义）→ 对话框关闭
3. agent 读**状态栏文本**（a11y）→ 仍是 `1.27 / 0.76` → **判定没提交**
4. `F4`（keyboard）重开对话框
5. `click_xy` 三击（gui）选中字段全部内容 —— a11y **没有"三击"这个动作**
6. `type_text`（a11y 语义写）→ Note 报 `0 -> 7 characters`，确认字段是空的
7. `Return`（keyboard）→ 提交，状态栏变 `1.27 / 15.12`

**a11y 提供的真值发现了 a11y 通道自己的失败，再借 GUI 绕过去。**
这正是"通道不可互相替代"的具体形态。

### 每条通道**独有的**贡献（换成别的通道做不到）

| 通道 | 独有贡献 |
|---|---|
| a11y | slide 2 缩略图（170×115 无文字标签的小图，树里是 `panel "Slide 2"`）；四个**全都没有名字**的 spin button 里"哪个是 Position Y"只写在 description 里；状态栏那行精确到小数点的几何真值 |
| gui | 双击进编辑模式、三击选中字段——**a11y 没有这两个动作**；GIMP 画布定位（树里 canvas 节点数为 0） |
| keyboard | `ctrl+r` / `ctrl+s` / `F4` / `Return`——这些命令在界面上没有 agent 够得着的入口 |

### 但要说清一个区别

WeaveBench 的 hybrid 是 **GUI + CLI/code**（持久态靠 shell）。
我们这里量到的是 **GUI 内部的三通道 hybrid**（a11y / gui / keyboard），
是另一个轴。测试时我**刻意禁掉了 Bash/Read/Write/Edit**，否则 agent 会直接
用 python-pptx 改文件，测的就不是 GUI 链路了。

**真实 Claude Code 会话里 agent 本来就有 Bash**，所以 GUI+CLI 那种 hybrid
是默认可用的——只是那样就测不出 MCP 本身的质量。两种 hybrid 都成立，
但要分开说。
