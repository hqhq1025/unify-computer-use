## 一、a11y 在 Impress 上比预期强得多

这是**和 GIMP 画布完全相反**的一例。GIMP 整棵树里 `canvas` 角色节点数为 0；
Impress 把幻灯片内容整个结构化了：

```
24 panel PageShape: Weekday in school     ← 幻灯片
25 panel PlaceHolder 1                     ← 标题占位符
  26 paragraph Value: Weekday in school    ← 文字内容
27 panel PlaceHolder 2
29 panel Right Arrow 3                     ← 形状
31 image Picture 4 Description: none.png   ← 图片
33 document frame Slides View
  34 panel Weekday in school [selected]    ← 排序器，逐页可寻址
  35 panel Slide 2
```

值得单独说的四点：

1. **shape 名字与文件格式完全一致**。a11y 报 `PlaceHolder 1`，python-pptx
   从 `.pptx` 里读出来的 `shape.name` 也是 `PlaceHolder 1`。VLM 看到的是一张
   渲染图，"哪块是标题"只能靠像素推断；a11y 直接给出文件格式里的那个名字。
2. **菜单树不展开就整棵可见**，而且 `radio menu item Right [checked]` 这种
   状态位是**当前格式的可靠真值**——比元素自己的几何可靠得多（见局限 2）。
3. **「位置和大小」对话框（F4）完全暴露**，且语义带在 Description 里：
   ```
   5 spin button Value: 0.76 cm  Description: Enter the vertical distance…   ← Y
   6 spin button Value: 1.27 cm  Description: Enter the horizontal distance… ← X
   ```
   这些 spin button **本身没有名字**，"哪个是 Y" 只能从 Description 得到。
   VLM 得靠标签与输入框的空间邻近去配对。
4. **状态栏把选中对象的几何以文本发布**：`1.27 / 0.76  22.86 x 3.17`。
   这是一条精确、可解析、由应用自己维护的几何真值。

## 二、九条局限（按严重程度；第 1 条已撤回）

### 1. ❌ 已撤回：「坐标系不一致」是我看错了

**原文说**：树里的 `Frame` 是窗口相对坐标、`click`/`drag` 的 `x`/`y` 是屏幕坐标，
差一个窗口原点，并把它列为"设计 VLM 模式第一件要定死的事"。**这是错的。**

查 `runtime.py` 的 `screen_point()`：裸 `x`/`y` 与元素锚定走的是**同一条**转换，
两者都是 `window_bounds + 相对坐标`。也就是说 `click`/`drag` 的 `x`/`y`
**本来就是窗口相对坐标**，和树里的 `Frame` 同一个坐标系。

而且截图也在同一个框里：`build_snapshot()` 把同一份 `bounds = extents(window)`
同时喂给 `render_tree()` 和 `capture_window_png()`，所以

> **截图像素 (0,0) ＝ 树 `Frame` 的原点 ＝ `click`/`drag` 的 `x`/`y` 原点。**

三条通道坐标系一致，这对 VLM 模式反而是**已经就位**的好消息，
不是待办。原结论把一个不存在的问题排成了第一优先。

**我为什么会看错**：任务 2 那次成功的拖拽，我在屏幕坐标系里算好数再传进去，
结果是对的——但那是因为**平移拖拽对常数偏移免疫**（起点和终点同加一个量，
位移不变），不是因为偏移存在。拿一次"结果正确"去反推机制，推错了。

真正的教训不在坐标系，而在**验证方法**：我用的是"改了之后好像好了"，
而不是去读那 10 行实现。读代码只要 30 秒。

### 2. 元素的 extents 会撒谎

右对齐生效后，段落节点的 `Frame` 仍然是 `{x: 314, width: 60}`——指向占位符
**左端**；截图里文字明明在右端。持续 8 秒复查不变，**不是刷新延迟，是报错**。

判定依据：截图 + 侧栏对齐按钮高亮 + `radio menu item Right [checked]`。

### 3. 「什么都没变」判据的假阴性

| 动作 | 工具的话 | 实际 |
|---|---|---|
| `ctrl+r` 右对齐 | "送达但被忽略，重复无用" | **生效了**（菜单里 Right 是 `[checked]`） |
| `ctrl+s` 保存 | "送达但被忽略，重复无用" | **保存了**（文件 mtime 与大小都变了） |

共同成因：**效果不在 a11y 树里**。格式属性、文件状态都没有树表示，
于是"树没变"被当成了"动作没生效"。

这与 backlog 里已记的第 3 类失败（状态变了行为没变）是**镜像**：
这里是**行为变了状态没变**。两者都接不住，但方向相反，处置也不同。

### 4. 假失败报告会把自己变成真失败

实测链条：点 `Discard` → 工具报 `appNotFound` → 我按报告重试 →
**其实每次都生效了**，叠出两个一模一样的 `Question` 对话框 →
关掉一个之后树"看起来没变"（还有一个一样的）→ 工具又报"没生效"。

一个假失败报告制造了真失败。这是"工具不许替 agent 打包票"的**反向**破口：
不许谎报成功，也不许谎报失败。

### 5. VCL 数值字段写不进去，且没有办法清空文本字段

四种组合全试过，控件文本都变了，应用**从不采纳**：

| 写入方式 | 提交方式 | 结果 |
|---|---|---|
| `set_value "15cm"` | 点 OK | 未采纳 |
| `set_value "15.00 cm"` | 点 OK | 未采纳 |
| `set_value "15.00 cm"` | Tab 失焦 | 未采纳 |
| `set_value "15 cm"` | Return | 未采纳 |

而且**没有任何办法清空一个文本字段**：
- `set_value` 能替换文本，但应用不解析
- `type_text` 走 EditableText，只能在光标处**插入**
- `ctrl+a` 与三击都选不中字段内容

于是连续尝试的结果是 `0.76 cm` → `150.76 cm` → `1515cm0.76 cm`。
**这是一个具体、可补的工具缺口。**

### 6. 模式状态在树里不可见

Impress 的「对象选中」和「文本编辑」是两种模式，同一个操作行为完全不同：

| 操作 | 对象选中态 | 文本编辑态 |
|---|---|---|
| `ctrl+r` | 无效 | 生效 |
| 拖拽 | 移动对象 | 选中文字 |

树里**没有**任何节点表示当前处于哪种模式。唯一线索是状态栏文本
`TextEdit: Paragraph 1, Row 1, Column 10`——一条要靠字符串匹配才能读懂的信息。

### 7. 拖拽必须从对象**边框**起手，从内部拖会进文本编辑模式

Impress 里对一个**已选中**的文本框，从**内部**按下拖动 → 进入文本编辑并选中文字；
只有从**边框**按下拖动才移动对象。

**做过对照实验**：用 xdotool 发一次"标准"拖拽（显式中间移动 + 每步 60ms 延时）
从内部起手，结果同样进入文本编辑模式。所以**这不是本仓库 `send_drag` 的实现
问题，是 Impress 的行为**。从上边框（`y = 对象 top + 1px`）起手，一次成功。

这类知识既不在 a11y 树里，也不在截图里——它是**应用特定的交互约定**。
VLM 同样看不出来。这是第三类知识，两条观测通道都给不了。

### 8. `press_key` 的 Escape 退不出文本编辑模式

实测连发 Escape、以及 `focus_window` 早退（窗口已 ACTIVE 时不抢焦点，
所以不是工具把状态改回去的）都无效，截图确认状态栏 `TextEdit: …` 不是陈旧数据。

**可用的绕法**：点幻灯片空白处（清空选择 + 退出编辑）→ 按 `Tab`（选中第一个
对象，且**不会**进入编辑模式）。状态栏立刻变成
`Title text 'Product ...' 'PlaceHolder 1' selected`，这是可靠的模式判据。

### 9. `element_index` 跨对话框开关会整体错位

F4 打开对话框后索引全变；用上一份快照的索引会**寻址到完全不同的控件**。
实测后果：本想点 Position Y，实际点到菜单，误把对象高度改成了 16.26cm。
（这次是我自己没重新取快照，工具的陈旧索引校验对"新快照里恰好也有该下标"
这种情况接不住。）

## 三、对 VLM 模式的设计意见

1. ~~先把坐标系定死~~ ~~给 `drag` 加元素锚定~~ —— **两条都已撤回。**

   坐标系三条通道本来就一致（见局限 1）。而"给 `drag` 加元素锚定"这条，
   查完 macOS 侧之后也站不住：

   | 实现 | `drag` 参数 |
   |---|---|
   | 官方 Codex（macOS，逆向记录） | `from_x/from_y/to_x/to_y` |
   | 本仓库 macOS Kit | 同上 |
   | 本仓库 Linux | 同上 |

   三处一致，而且逆向文档里写明了理由：
   > `drag` 只有坐标模式，没有 `element_index`，所以稳定性最依赖截图坐标选点。

   **不是遗漏，是上游的设计。** 而且本次实测正好印证了它的道理——
   元素锚定对我这个任务**两端都没用**：
   - **起点**：我需要的是标题框的**上边框**，元素锚定只会给中心点，
     而中心点恰恰是失败的那个位置（进了文本编辑模式）
   - **终点**：「幻灯片下方 15cm 处」根本不是一个元素

   > 拖拽的**目标位置通常不是元素**。这就是元素锚定解决不了它的根本原因。

2. **`drag` 是唯一一个截图不可选的工具。** 这是本轮对 VLM 模式最具体的结论。

   官方 `get_app_state` 的返回里**始终带当前窗口截图**，`x`/`y` 的定义就是
   "按截图像素坐标"。本仓库为了省 token 把截图改成了 `get_screenshot` 显式索取
   （见 `build_snapshot` 的 docstring）——对元素可寻址的动作这个取舍是对的，
   **但对 `drag` 不成立**：它既没有元素可锚，动作后的效果又基本不进 a11y 树
   （本次那个拖拽，树里的 `Frame` 一点没变，只有状态栏文本变了）。

   所以 `drag` 前要有截图选点、后要有截图验证。这是一条**窄而可辩护**的规则，
   比"整体切 VLM 模式"精确得多。

3. **VLM 不是 a11y 的替代，是它的验证通道**。本次两个假阴性（对齐、保存）
   靠截图一眼就判掉了；反过来，"哪个框是 Position Y" 靠截图要猜，靠 a11y 的
   Description 是确定的。**两条通道的强项正好互补，不是替代关系。**
4. **优先把应用自己发布的文本真值纳进来**。状态栏的
   `1.27 / 0.76  22.86 x 3.17`、菜单项的 `[checked]`——它们既比元素几何可靠，
   又比截图便宜。这类"应用自述"应该被当成第三种观测通道单独对待。
5. **补上"清空字段"和"选中字段全部内容"的能力**。局限 5 是纯工具缺口。
6. **把模式状态显式化**。至少把状态栏文本提到快照的固定位置，
   而不是埋在两百多个节点里等 agent 自己去 grep。
7. **承认存在两条通道都给不了的第三类知识**：局限 7（必须从边框拖）
   既不在树里也不在截图里，是应用特定的交互约定。VLM 模式解决不了它。
   这类知识只能靠**任务级的应用知识库**，或靠 agent 从失败里学。
   把它和"a11y 看不见"混为一谈，会高估 VLM 能补的那部分。

### 一条方法论收获

任务 2 之所以一度"做不到"，是**三个各自不致命的障碍叠在一起**：
坐标系偏了 + 退不出编辑模式 + 拖错了起手位置。任何一条单独出现都能绕过去，
叠起来就表现为"这条路走不通"。

而**闭环验证是解开它的关键**：状态栏的 `1.27 / 0.76 → 1.27 / 15.00` 让每一步
都能立刻判定成败，不用猜。没有这条真值通道，三个障碍会互相掩护，
根本分不清是哪一个在挡路。
